## 1. 目的

Shadowverse: Worlds Beyondにおいて、現在の山札または40枚デッキから、目的カードへ到達する確率を計算する。

利用者の入力負担に合わせ、同じ計算基盤を使う2種類の画面を提供する。

1. 簡易版
   - 入力項目を最小化する。
   - 「残り30枚、対象3枚、あと10枚」のような問いへ即答する。
   - 必要な場合だけサーチ設定や詳細結果を展開する。
2. 詳細版
   - Deck Portal URL、QR画像、デッキリストを読み込む。
   - 複数目標、マリガン、条件付きサーチ、連鎖を扱う。
   - 目的達成率が最大となる使用順と使用回数を自動探索する。

## 2. 設計原則

### 2.1 操作性

- 初期画面では、現在の判断に不要な設定を見せない。
- 簡易版の主要結果は、入力変更後すぐに再計算する。
- 詳細結果、回数別比較、計算根拠は折りたたみへ置く。
- 詳細版では、複雑な設定を段階式ウィザードに分割する。
- PCとスマートフォンの両方で利用できるレスポンシブUIにする。

### 2.2 計算の透明性

- 正確計算とモンテカルロ近似を明確に区別する。
- 近似へ切り替えた場合、試行回数、乱数シード、95%信頼区間を表示する。
- サーチカードのPP、盤面、固有条件を成立済みと仮定することを、結果付近に常時表示する。
- 自動探索は、未知の山札順を参照してはならない。
- 対応していないカードや未確認ルールを、対応済みとして扱わない。

### 2.3 保守性

- カード基本情報と確率計算用の効果定義を分離する。
- カード文章を実行時に自然言語解析しない。
- 新弾対応は、カードマスター更新、候補抽出、人間レビュー、効果定義追加、回帰試験の順に行う。
- 簡易版と詳細版は、同一の確率計算ライブラリとカード定義を使用する。

## 3. 対象範囲

### 3.1 対応するもの

- 40枚デッキ
- 現在の山札枚数と残存カード枚数
- 1つまたは複数の目的カード・目的グループ
- 次のN枚で引ける確率
- 0枚、1枚、2枚以上などの分布
- 期待枚数
- 50%、80%、90%へ到達するまでの必要枚数
- 4枚の初期手札とマリガン
- 通常ドロー
- 条件指定サーチ
- 指定された条件付きサーチ
- サーチからサーチを引く連鎖
- サーチの使用回数別比較
- 指定した目的関数に対する自動最適化
- 正確計算とモンテカルロへのフォールバック

### 3.2 初期版では対象外とするもの

- 対戦全体の完全再現
- PPが実際に足りるかの判定
- 盤面に必要カードがあるかの判定
- 相手の行動
- 戦闘、破壊、回復、ダメージの最適化
- カード文章の完全自動解釈
- 条件なしで任意のカードを引くだけの通常ドローカード効果
- アンリミテッド、スターター、インフィニティ
- 期限付き4桁デッキコードの直接取得
- QR画像そのもののサーバー保存

ターン開始時の通常ドローと、簡易版で指定する「次のN枚」は確率計算の基礎として残す。「通常ドローを対応しない」とは、通常ドローだけを行うカード効果を対応カードとして登録しない、という意味とする。

## 4. 用語

| 用語 | 定義 |
|---|---|
| 山札 | 現在デッキ領域に残っているカード |
| 目的カード | 引ける確率を求めるカード |
| 目的グループ | 複数カードをOR条件などでまとめた集合 |
| 通常ドロー | 条件を指定せず山札から引く処理 |
| 条件指定サーチ | フォロワー、クラス、コストなど、条件に一致するカードだけを引く処理 |
| 使用上限 | その計算中にカード効果を使用できる最大回数 |
| 強制使用 | 指定回数を必ず使う計算 |
| 最適使用 | 0回から使用上限までの中で目的関数を最大化する計算 |
| 到達 | 目的条件を満たす枚数を手札へ加えた状態 |
| 厳密計算 | 全状態を列挙または集約し、近似なしで求めた確率 |
| 近似計算 | モンテカルロ試行から推定した確率 |

- デッキから自動で対象枚数を数えたい。

- マリガン表を再現したい。
- 条件付きサーチを複数連鎖させたい。

## 6. 簡易版

### 6.1 基本入力

| 項目 | 型 | 初期値 | 制約 |
|---|---|---:|---|
| 現在の山札枚数 | 整数 | 30 | 1～40 |
| 目的カード残存枚数 | 整数 | 3 | 0～山札枚数 |
| 掘る枚数 | 整数 | 10 | 0～山札枚数 |

「残り30枚、対象3枚、あと10枚」の初期例では、1枚以上引く確率は約71.9212%となる。

### 6.2 目的カードの追加

- 「目的を追加」で複数グループを設定できる。
- 初期表示は1グループだけとする。
- 条件は次から選ぶ。
  - いずれかを1枚以上
  - すべてを1枚以上
  - カードごとの必要枚数
  - 合計N枚以上

### 6.3 サーチ設定

サーチ設定は初期状態で閉じる。

「サーチを追加」を開いた場合、次を入力する。

| 項目 | 内容 |
|---|---|
| 名称 | 任意の表示名 |
| 山札内のサーチカード枚数 | 0～3を基本とする |
| 使用上限 | 0～山札内枚数 |
| サーチ候補総数 | 現在の山札に残る該当カード数 |
| 候補内の目的カード数 | 目的ごとの該当枚数 |
| 1回で引く枚数 | 1以上 |
| 連鎖 | 有効／無効 |

サーチカードは、引いた時点で使用可能になる。PP、盤面、固有条件は成立済みと仮定する。

### 6.4 マリガン

簡易版では次の2種類だけを提供する。

1. 全返し
2. 目的カードのみキープ

マリガンを使用しない「現在の山札から計算」も選択できる。

### 6.5 主要出力

最適化した結果を代表値として上部へ表示する。

- 1枚以上引く確率
- 期待枚数
- 最適なサーチ使用回数
- 最適な使用順
- 計算方式

### 6.6 折りたたみ出力

- 0枚、1枚、2枚、3枚以上の分布
- 使用しない場合
- 必ず1回使う場合
- 必ず2回使う場合
- 0～上限の範囲で最適化した場合
- 50%、80%、90%へ到達する必要枚数
- 計算上の仮定

## 7. 詳細版

詳細版は、以下の5ステップで設定する。

### 7.1 ステップ1: デッキ入力

入力方式は次の3種類とする。

1. Deck Portal URL
2. QRコード画像
3. カード名と枚数の貼り付け

生の`hash=...`文字列だけを入力する欄は設けない。

読み込み後、カード一覧、合計枚数、クラス、フォーマット、エラーを表示する。

### 7.2 ステップ2: 計算開始状態

次から選択する。

1. ゲーム開始時
   - 40枚デッキ
   - 初期手札4枚
   - マリガンあり
2. ゲーム途中
   - 現在の山札枚数
   - 山札に残っている各カード枚数
   - 既知の手札
   - 既に使用したサーチ回数

### 7.3 ステップ3: 目的条件

目的条件はツリーとして保持する。

```text
AND
├─ OR
│  ├─ カードAを1枚以上
│  └─ カードBを1枚以上
└─ カードCを2枚以上
```

UIでは、初期版で次のテンプレートを提供する。

- AまたはBを引く
- AとBを両方引く
- AをN枚引く
- グループ合計でN枚引く

自動探索で最大化する目的条件は1つ選択する。その他の条件は参考値として同時表示できる。

### 7.4 ステップ4: マリガン

#### 7.4.1 プリセット

- 全キープ
- 全返し
- 目的カードだけキープ
- 目的カードとサーチカードをキープ
- カスタム

#### 7.4.2 カスタムルール

マリガンルールは自然言語ではなく、ルールビルダーで設定する。

対応するルール種別:

1. 単独キープ
2. カテゴリキープ
3. カテゴリ枚数上限
4. セットキープ
5. ユーザー定義条件
6. 優先順位

参考マリガン表は、次のように構造化する。

```text
単独キープ:
  - 大遊戯世界
  - 鋼鉄の微睡み
  - ハッピーフラワー・サミー＆マリー
  - ラティカ

カテゴリ:
  ドロソ:
    上限: 2
    対象: ユーザー指定
    優先順位: ユーザー指定

セットキープ:
  - 条件: ドロソを1枚以上 AND リンクルを1枚以上
    行動: 条件を構成するカードをキープ

ユーザー定義条件:
  - 条件名: アグロ対面
    有効時キープ:
      - ブラスト
      - ティコ
      - アラ
```

セットキープと対面条件の名称・対象は、すべて利用者が定義する。

#### 7.4.3 競合解決

同じカードへ複数ルールが適用された場合、次の順で判定する。

1. 明示的な必ず返す
2. 成立したセットキープ
3. 成立したユーザー定義条件
4. 単独キープ
5. カテゴリキープ
6. カテゴリ上限と優先順位
7. 返す

競合時の最終判断と理由は、結果画面で確認できる。

#### 7.4.4 マリガンの確率規則

- 初期手札は4枚。
- 任意枚数を1回だけ引き直す。
- 返したカードは山札へ戻してシャッフルする。
- 返したカードと同じカード実体は、引き直し後の手札へ入らない。
- 同名の別カード実体は、引き直し後に入る可能性がある。

カード実体単位の除外を正確計算とモンテカルロの両方で再現する。

### 7.5 ステップ5: サーチ設定

カード定義から、デッキ内の対応カードを自動表示する。

表示順は、代表1～5を上部へ固定し、その後にその他の対応効果をカードID順で並べる。カード単位ではなく効果単位で表示し、`尽小花・イマリ ファンファーレ`と`尽小花・イマリ 超進化`のように区別する。

各効果について次を設定する。

- 有効／無効
- 最大使用回数
- 引いたら即使用可能
- 連鎖を許可するか
- 選択モード
- 強制使用か、最適化対象か

PP、盤面、進化、覚醒、土の秘術などの成立可否は自動判定しない。利用者がそのカードを有効にした時点で、効果の前提条件は成立済みとして扱う。

`叫喚と憎悪`はモード2とモード3の使用回数を別々に入力し、同時選択できる回数を考慮して必要カード使用回数を計算する。`尽小花・イマリ`もファンファーレと超進化の使用回数を別々に入力する。

結果画面に次の注釈を常時表示する。

> 条件付きサーチは、対象カードを引いた時点で使用可能として計算しています。PP、盤面、進化、カード固有の発動条件を実戦で満たせない場合があるため、実際の到達確率とは異なる可能性があります。

## 8. カード効果モデル

### 8.1 自然言語から分離した構造化定義

カード効果は、カード文章とは別のJSONで管理する。

```json
{
  "schemaVersion": 1,
  "cardId": 10632310,
  "name": "正常の侵食",
  "reviewStatus": "verified",
  "activation": {
    "mode": "manual-enabled",
    "maxUsesDefault": 3,
    "assumptions": [
      "PP条件を満たす",
      "天晶の魔手を破壊できる"
    ]
  },
  "operations": [
    {
      "type": "draw-filtered",
      "count": 2,
      "filter": {
        "class": "witch",
        "cardType": "follower"
      },
      "distinctNames": false
    }
  ]
}
```

### 8.2 必要な操作型

| 操作型 | 内容 |
|---|---|
| `draw-filtered` | 条件に一致するカードからN枚引く |
| `draw-all-named` | 指定名の残存カードすべてを引く |
| `draw-distinct-names` | 同名重複なしでN種類を引く |
| `return-to-deck` | 手札からカードを山札へ戻す |
| `discard-from-hand` | 手札からカードを捨てる |
| `replace-hand` | 手札を戻して同数引く |
| `choose-mode` | 複数モードから使用モードを選ぶ |
| `repeat` | 条件に応じて操作を繰り返す |
| `conditional` | 成立済みと仮定する条件分岐 |

### 8.3 抽選規則

- 山札は無作為にシャッフルされているものとする。
- 通常ドローは、残存カード全体から重複なしで逐次抽選する。
- 条件指定サーチは、現在の山札で条件に一致するカードだけを母集団とする。
- 同じカード実体は2回引かない。
- 「N枚」は同名を重複して引き得る。
- 「N種類」は同名を重複して選ばない。
- サーチ候補が必要枚数未満の場合は、存在する候補だけを引く。
- サーチで別の有効なサーチカードを引いた場合、連鎖設定が有効なら新しい選択肢へ追加する。

### 8.4 対応カード

通常ドローだけを行うカード効果は対応対象から除外し、ユーザーがレビューしたサーチ効果だけを登録する。

- 対応カード: 15枚
- 対応効果: 17件
- 代表効果: 5件
- 公式Q&Aによる追加例外: なし

対応表:

- [対応サーチカード一覧_v0.1.md](./対応サーチカード一覧_v0.1.md)

表示順:

1. 代表1 正常の侵食
2. 代表2 空の命運を握る少女・ルリア
3. 代表3 蒼い空を征く騎空士・グラン＆ジータ
4. 代表4 叫喚と憎悪 モード2（フォロワーサーチ）
5. 代表5 叫喚と憎悪 モード3（3コストスペルサーチ）
6. その他をカードID順

同一カードでも効果が異なる場合は、効果ID、表示、使用回数を分離する。`叫喚と憎悪`はモード2とモード3、`尽小花・イマリ`はファンファーレと超進化を別効果として扱う。

## 9. Deck Portal URL

### 9.1 入力

完全なDeck Portal URLだけを受け付ける。

```text
https://shadowverse-wb.com/ja/deck/detail/?hash=...
```

### 9.2 処理

1. URLとして構文解析する。
2. HTTPSか確認する。
3. ホストが許可リスト内か確認する。
4. パスがDeck Portalのデッキ詳細か確認する。
5. `hash`クエリを取得する。
6. フォーマット、クラス、40枚のカード識別子へ分解する。
7. カードマスターと照合する。
8. 同名カードを集約する。
9. 40枚、クラス、投入可能枚数、ローテーション適格性を検証する。

カードごとに手作業で対応表を作る設計にはしない。必要なのは、次の2点である。

1. 64文字を0～63へ対応させる、1本のBase64類似アルファベット
2. 4文字の識別子とDeck Portal内部のカード番号を相互変換するアルゴリズム

標準Base64とは文字順が異なる可能性があるため、「Base64ライブラリへ文字列をそのまま渡す」実装にはしない。友人から得た`0-9`、小文字、大文字、記号という情報と、提供されたURLをテストベクトルにして変換規則を確定する。

確認済み事項:

- URLの先頭`1`はローテーション、次の`3`はウィッチを表す。
- 提供されたhashを公式Deck Portalの`deckHashDetail`へ渡すと、40枚とカードIDを取得できる。
- QRとURLはカードの並び順が異なる場合があるため、多重集合へ正規化して比較する。

未確定事項:

- 4文字識別子が公式カードIDを直接変換したものか、別の内部番号を変換したものか。
- 62番目と63番目の記号順。

直接変換が確認できれば、カード別対応表は不要である。別の内部番号を使用している場合だけ、カードマスター更新時に機械生成する`内部番号 → card_id`対応データが必要になる。このデータも手作業では作らない。

### 9.3 エラー

- URL形式ではない
- 許可されていないホスト
- `hash`がない
- 未知のフォーマット
- 未知のクラス
- カード数が40枚ではない
- 未知のカードID
- ローテーション外
- クラス不一致
- 投入上限違反

エラー時は、カード名・枚数貼り付けへ誘導する。

## 10. QRコード入力

### 10.1 入力方法

- ファイル選択
- ドラッグ＆ドロップ
- クリップボード貼り付け

### 10.2 検出手順

1. 画像のMIME、容量、画素数を検証する。
2. 画像全体からQRを検出する。
3. 失敗した場合、複数解像度へ縮小・拡大して再試行する。
4. 0度、90度、180度、270度を試す。
5. 失敗した場合、右上の広い領域を切り出して再試行する。
6. 二値化・コントラスト補正を試す。
7. 複数QRがある場合、Deck Portal URLだけを候補にする。
8. 復号したURLをDeck Portal URL処理へ渡す。

QRの固定座標には依存しない。右上はフォールバック探索範囲としてだけ利用する。

### 10.3 実画像の検証結果

提供された1920×1080のスクリーンショットは、画像全体からQRを検出できた。

- 検出範囲: およそ`x=1524～1734, y=84～294`
- 復号結果: Deck Portal URL
- 復号カード数: 40枚
- 提示された参考URLとの比較: 並び順は異なるがカードIDの多重集合は一致

この画像をQR回帰試験のフィクスチャとする。公開リポジトリへ画像を含める場合は、利用許諾とファイルサイズを確認する。含めない場合は、同等のテスト用QRを生成する。

### 10.4 プライバシーと負荷

- QR画像の解析はブラウザ内だけで行う。
- 原画像を収集APIへ送らない。
- 解析成功後、正規化したカードIDと枚数だけを分析イベントへ含める。
- 画像容量と総画素数に上限を設け、巨大画像によるメモリ枯渇を防ぐ。

## 11. 確率計算

### 11.1 単純ドロー

#### 11.1.1 根拠

デッキを無作為にシャッフルした後、山札N枚からD枚を重複なしで引く。取り出したカードを山札へ戻さないため、各試行が独立な二項分布ではなく、有限母集団からの非復元抽出となる。この条件に対応する分布が超幾何分布である。

山札N枚のうち目的カードがK枚あり、D枚の中に目的カードがちょうどx枚含まれる組合せを数える。

- 目的カードK枚からx枚を選ぶ方法: `C(K, x)`
- 目的外カード`N-K`枚から`D-x`枚を選ぶ方法: `C(N-K, D-x)`
- 山札N枚からD枚を選ぶ全方法: `C(N, D)`

したがって、確率は次になる。

```text
P(X = x) = C(K, x) * C(N-K, D-x) / C(N, D)
```

1枚以上引く確率は、0枚も引かない確率の余事象である。

```text
P(X >= 1) = 1 - C(N-K, D) / C(N, D)
```

期待枚数は分布から求められ、超幾何分布の期待値と一致する。

```text
E[X] = Σ x * P(X = x) = D * K / N
```

例として、山札30枚、目的カード3枚、10枚引く場合:

```text
P(X >= 1)
= 1 - C(27, 10) / C(30, 10)
= 0.719211822660099...
= 約71.9212%
```

#### 11.1.2 条件指定サーチ

サーチ時点の山札で、条件に一致するカードがM枚、その中に目的カードがT枚あり、そこからS枚を引く場合も、母集団をM枚へ限定した超幾何分布になる。

```text
P(Y = y) = C(T, y) * C(M-T, S-y) / C(M, S)
```

1枚サーチの場合は`T / M`となる。「2種類を引く」はカード名単位の非復元抽出なので、同名カード枚数だけで集約せず、種類ごとの状態を保持する。

#### 11.1.3 複数目的

複数のカード群を同時に数える場合は、多変量超幾何分布を使う。目的外カードも1つの群に加え、`ΣKi=N`、`Σxi=D`となる排他的な群へ分割する。各群から引く枚数を`x1...xr`、各群の残存枚数を`K1...Kr`とすると、同時確率は次になる。

```text
P(X1=x1,...,Xr=xr)
= Π C(Ki, xi) / C(N, D)
```

群が重複する場合は、そのまま独立な群として扱わず、所属パターンごとの排他的なカード群へ分割してから計算する。

#### 11.1.4 マリガン、連鎖、自動探索

- マリガンは、初期4枚の各パターンの確率と、そのパターンにルールを適用した引き直し後の条件付き確率を、全確率の法則で合計する。
- サーチ連鎖は、現在状態から起こり得る次状態を列挙し、`遷移確率 × 次状態の確率`を合計する。
- 使用順の自動最適化は、観測済み状態ごとに目的達成確率が最大となる行動を選ぶ動的計画法で求める。
- これらは超幾何分布とは別の近似式を使うのではなく、超幾何分布で得た各遷移確率を状態木上で合成する。

#### 11.1.5 数値計算

- 小さい組合せは整数または逐次比で計算する。
- 桁が大きい場合は対数階乗または確率比を使用する。
- 0除算、母集団不足、候補不足を明示的に処理する。
- 同じ入力では、丸め前の内部値が一致することを単体試験で確認する。

### 11.2 詳細版の状態

厳密計算では、目的に関係する同値カードを集約した状態を使用する。

```text
State:
  remainingCounts        山札内のカード群別枚数
  handCounts             手札内の関連カード群別枚数
  targetCounts           目的カード到達枚数
  normalDrawsRemaining   残り通常ドロー数
  availableEffects       現在使用可能な効果
  usedEffectCounts       効果別使用回数
  forcedUseCounts        強制使用回数
  mulliganState          初期手札・返却実体の状態
  modeSelections         固定されたカードモード
```

カード名が異なっても、今後の遷移と目的判定が完全に同じなら同じ群へ集約できる。

### 11.3 遷移

1. 通常ドロー
2. 新たに引いたカードを手札へ追加
3. 目的枚数を更新
4. 新しいサーチ効果を使用可能一覧へ追加
5. 強制使用条件を処理
6. 最適化対象の行動を列挙
7. 選択した効果を解決
8. 手札・山札・使用回数を更新
9. 連鎖があれば繰り返す
10. 終了条件を判定

### 11.4 自動探索

目的関数を満たす確率が最大となる方策を求める。

```text
V(state) = max_action Σ P(next_state | state, action) * V(next_state)
```

同率の場合の優先順位:

1. 使用カード枚数が少ない
2. 使用効果回数が少ない
3. 山札を多く残す
4. カードIDとモードIDの固定順

これにより、同じ入力と同じデータバージョンから同じ結果を得る。

探索が参照できる情報は、現在までに観測した手札、残存枚数、設定値だけとする。未来の山札順を見て行動を変える実装は禁止する。

### 11.5 使用回数比較

最大使用回数Mに対し、次を計算する。

- 必ず0回
- 必ず1回
- …
- 必ずM回
- 0～M回で最適化

簡易版は最適化結果を代表表示し、各回数は折りたたむ。詳細版は比較表を展開できる。

### 11.6 タイムアウト

- 厳密計算はWeb Worker内で行う。
- 厳密計算のタイムアウトは100msとする。
- 100msは厳密計算だけの制限であり、モンテカルロの実行時間上限ではない。
- 利用者向け設定からは変更できない固定値とする。
- UIスレッドをブロックしない。
- タイムアウト時は厳密計算を中断する。
- 途中までの値を正確な結果として表示しない。
- 同じ入力をモンテカルロへ渡す。

### 11.7 モンテカルロ

初期設定:

| 項目 | 値 |
|---|---:|
| 最低試行回数 | 100,000 |
| 最大試行回数 | 1,000,000 |
| 目標95%信頼区間半幅 | 0.5ポイント |
| モンテカルロ時間上限 | 5秒 |
| 乱数 | シード指定可能なPRNG |

100,000試行ごとに結果を更新し、次のいずれかで終了する。

1. 目標信頼区間へ到達
2. 最大試行回数へ到達
3. 追加時間上限へ到達
4. 利用者が中止

二項確率の区間推定にはWilson区間を使用する。期待枚数には標本平均と標準誤差を表示する。

近似最適化では、未来の山札順を使わない観測可能状態単位の方策を評価する。同じ候補方策の比較には共通乱数を使い、分散を抑える。

#### 11.7.1 所要時間の事前計測

製品実装前の参考値として、Node.js上の一時JavaScriptベンチマークを2026-07-30に実行した。保存される製品コードは作成していない。

計測内容:

- 単純ケース: 山札30枚から10枚を非復元抽出
- 代表ケース: 40枚シャッフル、初期4枚、10回の観測ドロー、最大3回の条件指定サーチ
- 各条件を5回計測し中央値を採用

| ケース | 試行回数 | 中央値 | 最小～最大 |
|---|---:|---:|---:|
| 単純ケース | 100,000 | 5.01ms | 3.03～25.37ms |
| 代表ケース | 100,000 | 19.71ms | 17.79～21.42ms |
| 単純ケース | 1,000,000 | 40.69ms | 38.09～47.39ms |
| 代表ケース | 1,000,000 | 198.60ms | 191.92～200.70ms |

この値には、React描画、Web Workerの起動・通信、複数目的の評価、マリガンルール、方策探索、低性能スマートフォンの影響が含まれない。したがって本番の保証値にはしない。

実利用の暫定見積り:

| 端末・条件 | 100,000試行 | 1,000,000試行 |
|---|---:|---:|
| 一般的なPC、単純～中程度 | 約20～200ms | 約0.2～2秒 |
| スマートフォン、複雑な連鎖 | 約0.1～1秒 | 約1～5秒超 |

モンテカルロは100,000試行終了時に最初の結果を表示し、その後バックグラウンドで精度を上げる。5秒へ達した場合は、その時点の試行回数と信頼区間を結果として確定する。

#### 11.7.2 試行回数と誤差

達成回数を`S`、試行回数を`n`とすると推定値は次である。

```text
p_hat = S / n
```

単純な標準誤差の目安は次であり、`p=0.5`付近で最大になる。

```text
SE ≈ sqrt(p_hat * (1 - p_hat) / n)
```

最悪条件付近の95%区間半幅の目安:

- 100,000試行: 約0.31ポイント
- 1,000,000試行: 約0.10ポイント

画面上の正式な区間表示には、端の確率でも安定するWilson区間を使用する。

- 初期手札は4枚。
- 全返しが正しい分布になる。
- 目的カードのみキープが正しい分布になる。
- 返したカード実体を引き直しで再取得しない。
- 同名の別実体は再取得し得る。
- カテゴリ2枚上限が優先順位どおりに働く。
- セットキープが成立・不成立で分岐する。
- ユーザー定義条件の有効／無効が反映される。

### 17.3 サーチ

- 通常ドローと条件指定サーチの母集団が異なる。
- 2枚サーチが重複なしで処理される。
- 2種類サーチで同名を重複選択しない。
- サーチで引いたサーチが連鎖する。
- 使用回数上限を超えない。
- 強制0～M回と最適使用の比較が一致する。
- 自動探索が未来の山札順を参照しない。

### 17.4 タイムアウト

- 厳密計算のWeb Workerが100msで中断される。
- 部分的な厳密値を表示しない。
- モンテカルロへ自動移行する。
- 近似表示、試行回数、シード、信頼区間が出る。
- モンテカルロは100,000試行時点の途中結果を表示する。
- モンテカルロは5秒上限または1,000,000試行で終了する。

### 17.5 Deck Portal・QR

- 提供された参考URLから40枚を復号する。
- 提供されたQRスクリーンショットから同じ40枚を復号する。
- URLとQRの並び順が異なっても同じデッキと判定する。
- 右上以外のQRも検出する。
- 回転、縮小、余白、異なるアスペクト比を処理する。
- 不正ホストと不正URLを拒否する。

### 17.6 収集

- 公開ソース単体のビルドは収集APIへ通信しない。
- 本番Worker経由だけ収集スクリプトが挿入される。
- QR原画像を送らない。
- 同じデッキが同じフィンガープリントになる。
- アンケートは初回に出ない。
- アンケートは30日以内に再表示しない。
- 日本国外ではアンケートを表示しない。
- 収集API停止中も計算できる。
- データ識別IDによる削除が関連テーブルへ反映される。

### 17.7 管理画面・フッター

- `/hugfire`以外から管理画面へ到達しない。
- パスワード欄へ英数字以外を入力できない。
- サーバー側も英数字以外を拒否する。
- 環境変数未設定時は管理機能を開かない。
- 認証Cookieが`HttpOnly`、`Secure`、`SameSite=Strict`になる。
- フッターには指定Xアカウントへのリンクだけが表示される。
- フッターへ「問い合わせ」「削除要請」などの用途説明が表示されない。

## 18. 受入条件

### 18.1 簡易版

- 3つの基本数値だけで結果が出る。
- サーチ設定を閉じたまま利用できる。
- 最適結果が代表表示される。
- 回数別結果を折りたたみで確認できる。
- マリガンは全返しと目的カードのみキープを選べる。

### 18.2 詳細版

- Deck Portal URL、QR、貼り付けからデッキを読み込める。
- 複数目的を設定できる。
- マリガン表相当の単独、カテゴリ上限、セット、ユーザー定義条件を設定できる。
- 対応済みサーチ効果を自動表示できる。
- 使用回数ごとの比較と最適順を表示できる。
- 100ms超過時に近似へ切り替わる。

### 18.3 運用

- 17件の対応効果が対応表どおりに表示される。
- 新弾カードを構造化定義へ追加できる。
- Public GitHubに収集API実装、D1、認証情報を含めない。
- 本番分析データを非公開管理画面から集計できる。

## 21. 確定済み判断

- 簡易版と詳細版を同じサイト内に用意する。
- 簡易版ではサーチ設定を折りたたむ。
- 詳細版はサーチ連鎖へ対応する。
- 使用なし、回数固定、最適使用を比較する。
- 自動探索で目的条件を最大化する。
- PP、盤面、固有条件は成立済みと仮定し、注釈を表示する。
- マリガンは簡易版と詳細版で機能を分ける。
- 詳細版はユーザー定義のセット条件と対面等の条件を扱う。
- レビュー済み15枚・17効果のサーチだけを対応対象とする。
- 代表1～5を上部へ番号順で表示する。
- 叫喚と憎悪、尽小花・イマリは効果ごとに別表示する。
- 通常ドローだけを行うカード効果は対応しない。
- Deck Portal URL、QR、貼り付けへ対応する。
- 生のhash入力欄は設けない。
- QRは画像全体から検出し、右上固定座標へ依存しない。
- 正確計算がタイムアウトした場合、モンテカルロへ切り替える。
- 厳密計算のタイムアウトは100msとし、モンテカルロには別の5秒上限を使う。
- Cloudflare Pagesで公開する。
- サイト名とリポジトリ名は「ドロー確率計算機」とする。
- 推奨公開ドメインは`shadowverse-draw-calculator.pages.dev`とする。
- Cloudflareアカウントとリポジトリはユーザー本人が所有する。
- 非公開管理画面は`/hugfire`とし、英数字パスワードを環境変数で設定する。
- フッターにはXアカウントだけを表示し、用途説明は表示しない。
- 本番収集処理は非公開WorkerとD1へ分離する。
- デッキ、マリガン、利用履歴、任意アンケートを収集する。
- 日本国外では任意アンケートを表示しない。
- Public GitHubのREADMEには、本番収集による環境差を記載しない。
